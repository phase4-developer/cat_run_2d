## MV-FW-REUSE-ECONOMY

- 2026-11-19 `fd0861dc`에서 공용 재화 표시 부품을 개발할 때 `manifest.json`은 이미 `com.jjevol.ui.economy` pre.6을 연결하고 있었다. 당시 고정 tgz의 `ResourceLabel`에도 재화 ID로 수량·아이콘을 읽고 변경을 구독하는 API가 있었다. 원장 `MV-UI3-HUD2`의 검증은 새 부품의 연결과 동작을 확인했고, 기존 API로 요구를 충족할 수 있는지 비교한 근거는 그 계약 기록에서 찾지 못했다.
- 11-20 중앙 요청 `6113efd233c5`에서 새 구현 전에 기존 API와 직접 구현 사유를 확인하는 규칙이 추가됐다. 11-23 `MV-UI-ICONSRC`는 공용 재화 칸의 아이콘 출처를 표로 고쳤지만 잔액 라벨 교체까지 이어지지 않았다. 11-25 `cf104ad0`도 인스펙터 문자열과 프리젠터의 고정 목록이 어긋나는 증상만 수정했다. 새 구현에 대한 확인과 기존 코드 수정에서의 재사용 검토가 함께 작동해야 한다.
- 중앙 개선 제안은 화면에서 새 부품을 연결하거나 기존 구현을 수정할 때, 역할별로 실제 고정 패키지의 API와 사용 중인 프리팹·호출부를 짝지어 검토하는 것이다. 공통 기반 클래스 상속과 해당 기능의 재사용은 다른 증거다. 직접 구현 사유가 있으면 표시 값의 소유자와 동작 차이를 기록하고, 회귀 시험은 프리팹 설정 변경과 실제 데이터 공급 경로를 확인한다. 기존 검토 항목을 이 근거로 보강한다.
- 환생·Area 강화·로비의 저장 보유량은 Framework `ResourceLabel.ShowUI`와 `MvConsumePresentation`을 사용한다. 인게임 재화는 런 스냅샷에서 계산되므로 `HudCurrencySlot`의 직접 표시가 필요하다. 두 경로는 공용 `Slot_Currency` 프리팹을 쓴다.

## 패키지 갱신 후 전환이 빠진 사용처

- 결과 팝업(`be2230b8`)과 지도 진행 팝업(`29777dfd`)을 만들 때의 `ui.contracts` 고정본에는 `FloatTween`이 없었다. `a2e47221`에서 사용 가능해진 뒤 계단 게이지 전환은 기록됐고 결과·지도 진행률의 프레임 보간은 남았다. 직렬화된 시간·곡선과 닫기 순서는 각 화면에서 관리하며 경과 시간에 따른 진행률을 `FloatTween`으로 옮길 수 있다.
- 드롭 추첨은 D-85에서 고정본 도입 뒤 전환하기로 했고 `economy.drop`이 이미 연결됐다. 현재 `MvDropRoller`의 0 수량은 일부 지급식의 유효한 입력이며 Framework는 0 수량 결과를 생략한다. 난수 호출과 중첩 행 출처도 함께 보존해야 하므로 어댑터 계약 및 런 결과 대조를 남긴다.
- 메타 요청과 광고는 패키지 설치 후 실제 부트·요청 경로 연결이 남아 있다. 메타는 `MV-PLAY-INT`에 남은 로컬 라우팅·응답 반영 과제에 해당한다. 광고는 기본 공급자가 가짜 광고로 남아 있으며, 기존 `MV-PLAT-ADS`와 D-ADS-1 기준에 따라 출시 경로의 공급자 연결 및 기기 검증이 필요하다.
- 패키지를 갱신할 때 기존 대체 구현과 재검토 대상을 패키지 갱신 기록에 연결한다. 같은 기능 이름이 있어도 표시 값의 출처, 게임 규칙, 기존 연출이 다른 사용처는 동작 계약과 함께 기록한다.

## MV-FW-REUSE-WORKFLOW

- 2026-11-25 기존 기능 조사와 중앙 보고가 한 요청에 들어오자 보고 명령의 위치를 오케스트라 적용 조건으로 확대 해석했다. 총괄 잠금을 잡고 읽기 전용 검토를 배정했다. 작업에서 필요한 운영 단위와 스킬의 기능을 먼저 대조했어야 한다. 사용자 지적 뒤 총괄 잠금을 해제했다.
- 영향은 작업 시작 단계의 불필요한 절차와 사용자 혼선이었다. 추가 검토에는 읽기 권한만 배정했다. 이 과정에서 다른 작업을 넘겨받거나 중앙 저장소·원격을 변경한 사실은 없다.
- 개선 제안은 `central_manager.py report`를 스킬 사용 여부와 독립된 보고 경로로 안내하고, 한 담당이 감당할 수 있는 수정은 기존 작업 폴더와 검증 절차로 처리하는 것이다. 프로젝트 총괄·작업 배정 절차는 실제로 별도 작업의 충돌 조정이나 인계가 필요한 때 적용한다. 파일 수·메시지 수·중앙 보고 포함 여부에 따라 일괄 승격하는 규칙은 두지 않는다.
