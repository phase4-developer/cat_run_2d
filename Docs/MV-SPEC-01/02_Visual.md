# 2. 비주얼 — 월드 렌더 재현

[입구](README.md) · 앞: [01 범위](01_Scope.md) · 다음: [03 리소스 파이프라인](03_ResourcePipeline.md)

이 절은 렌더 담당(`MV.View`, 작업 계약 MV-VIEW)이 Unity에서 정본과 **같은 화면**을 만들도록 투영·카메라·정렬·안개·테마·해상도·시간축을 정한다. 그림 추출과 아틀라스는 [03](03_ResourcePipeline.md), 이펙트·팝업·우다다 연출은 [06](06_Effects.md), 표 열의 최종 정의는 [07](07_Tables.md)이 정본이다.

정본 사실 먼저:
- 화면은 **Canvas 2D 함수 `draw2D`(L3777~3819)만** 그린다. three.js는 카메라 행렬·위치 계산에만 쓴다. 렌더러는 가짜 객체이고 `render(){}`가 비어 있다(L919~922 주석 「2D 버전: WebGL 없이 캔버스 2D로 그린다」). 일부 분석 노트의 「Three.js WebGL 화면」 서술은 틀렸다.
- 그래서 3D 전용 요소(원경 `farG` 산·구름·해, 풀 InstancedMesh, 조명·그림자, 계단 칸 메쉬)는 **화면에 나오지 않는다**. Unity에서도 그리지 않는다.

## 2.1 재현 방식

### 2.1.1 정본의 투영

```js
function pj(x, y, z){   // three 월드 좌표 → 화면 px. d: 깊이, s: 1m 당 px   (L2795~2799)
  _p.set(x, y, z).applyMatrix4(camera.matrixWorldInverse); const d = -_p.z; if (d < 0.3) return null;
  _p.applyMatrix4(camera.projectionMatrix);
  return {x:(_p.x + 1)/2*W, y:(1 - _p.y)/2*H, d, s:camera.projectionMatrix.elements[5]*H/2/d};
}
```

| 항목 | 값 | 근거 |
|---|---|---|
| 카메라 | `PerspectiveCamera(52, 9/16, 0.1, 400)`, 세로 FOV 52° | L924 [프로토] |
| d | 뷰 공간 전방 깊이(카메라 앞축 투영 거리, 유클리드 거리 아님) | L2796 |
| 근평면 컷 | `d < 0.3`이면 그 점(=그 그림 전체) 생략. 화면 밖 좌우·상하 컬링은 없음 | L2796 |
| s | 1 m당 px = `P[5]·H/2/d`, `P[5] = 1/tan(26°) = 2.0503` → `s = 1.0252·H/d` | L2798 [계산] |
| 그리기 | 모든 그림은 앵커 점 하나를 `pj`로 찍고, 그 점에서 **s배 균일 스케일**로 화면 정렬 그림을 그린다. 카메라 회전은 그림에 반영하지 않는다 | E 노트 §1.3 |
| 예외 | 지면 띠(`quad`), 담장 옆면, 빨랫줄, 전봇대, 창 궤적, 우물 벽돌 배치는 **여러 점을 각각 `pj`해서 이은다** → 진짜 원근 | L2870~2894, L3558~3569, L3545, L3585, L3802, L3644 |

### 2.1.2 좌표 규칙

| 좌표계 | 축 | 변환 |
|---|---|---|
| 게임(정본 규칙·표·`MV.Run`) | x 오른쪽, y 위, z 전진 | 기준 |
| three(정본 내부) | x, y, −z | `V(x,y,z) => (x, y, -z)` L940, `wpos` L2823이 역변환 |
| **Unity** | x 오른쪽, y 위, z 전진(왼손 좌표계) | **게임 좌표를 그대로 쓴다.** 변환 없음 |

규칙: 정본 코드에서 three 좌표를 다루는 곳(`_w`, `V(...)`, `camera.position.z`, `place`)을 옮길 때만 z 부호를 바꾼다. 예: 정본 `PZ = -camera.position.z`(L3781) = Unity `camera.transform.position.z`. 화면 회전 부호: 캔버스 `rotate(+a)`는 화면 y가 아래라 **시계 방향**이다. Unity 빌보드의 로컬 z 회전은 `-a`(도 단위 변환)로 넣는다.

### 2.1.3 권장 방식: URP 원근 카메라 + 카메라 평면 정렬 빌보드 (결정 대기 D-40)

| 항목 | 값 |
|---|---|
| 렌더러 | **URP Universal Renderer(Forward)**. 2D Renderer는 쓰지 않는다(원근 카메라·원근 메쉬·Unlit 커스텀 셰이더 구조, 2D 조명 불필요). 프로젝트 설정 `render_pipeline = urp`(Universal) 확정 |
| 카메라 | URP Base 카메라 `GameCamera`, Perspective, 세로 FOV 52(화면비 처리는 §2.7), near 0.1, far 400, 배경 Solid Color = 현재 테마 `fog` |
| 월드 그림 | `SpriteRenderer`(또는 같은 셰이더의 Mesh) **빌보드**. 회전 = `GameCamera.transform.rotation`을 매 프레임 `LateUpdate`에서 복사(카메라 이동 후). 카메라 쪽을 바라보는 구형 빌보드(LookAt 카메라 위치)는 쓰지 않는다 |
| 크기 | 스프라이트 1 unit = 1 m(PPU는 [03](03_ResourcePipeline.md)). 정본 함수의 `s` 배수 = Unity 로컬 m |
| 깊이 버퍼 | 쓰지 않는다. 월드 재질 전부 `ZWrite Off`, `ZTest Always`, 투명 큐. 앞뒤는 §2.3 정렬만으로 정한다(정본도 Z 버퍼 없는 화가 알고리즘) |
| 근평면 | Unity near 0.1은 화소 단위로 자른다. 정본처럼 **앵커 d < 0.3이면 그 그림 전체를 숨긴다**(`DepthSorter`가 처리) |

**왜 같은가.** 카메라 평면에 평행한 평면 위의 모든 점은 뷰 깊이 d가 같다. 원근 투영은 그 평면 위 길이 1 m를 정확히 `P[5]·H/2/d` px로 그린다. 이것이 `pj`의 s와 같은 식이다. 그러니 앵커를 같은 월드 점에 두고 그림을 카메라 평면에 평행하게 세우면 위치(같은 행렬로 투영)와 크기(같은 s, 균일)가 모두 정본과 일치한다. 구형 빌보드는 화면 가장자리에서 평면이 기울어 깊이가 달라지므로 어긋난다.

**옮기는 규칙(모든 그리기 함수 공통).**
1. 정본 함수 안의 `pj(...)` 호출 하나 = Unity 앵커 하나(빈 Transform, 월드 좌표, 회전 없음).
2. 그 앵커에서 `s` 배수로 그린 부분 = 앵커의 자식 **빌보드**(카메라 회전 복사). 로컬 좌표 = 정본 수치(m). 정본 화면 y는 아래가 +이므로 로컬 y는 부호를 바꾼다.
3. 여러 `pj` 점을 이어 그린 다각형·선(`quad`, `poly`, `LN`) = 그 점들을 정점으로 하는 **월드 메쉬**(회전하지 않음).
4. 한 그리기 함수 안의 그리는 순서 = 자식 `sortingOrder` 오름차순(같은 `SortingGroup` 안, §2.3).
5. 선 굵기처럼 `Math.max(1, s*k)` 형태로 px 하한·상한이 있는 값은 기준 해상도(높이 640, 플레이어 깊이)에서의 m 값(= k)으로 굽는다. 하한·상한 차이는 [12](12_Acceptance.md)의 허용 오차로 본다.

## 2.2 카메라

### 2.2.1 정본 공식 (`syncScene` L2746~2779)

```js
camLift += ((WY + (C ? py : 0)) - camLift)*Math.min(1, dt*(C ? 12 : 6));
ui.ck  += ((C ? 1 : 0) - ui.ck)*Math.min(1, dt*(C ? 3 : 2));
camPos = V(px*0.25, camLift + 13 + 2*ck, pz - 9 - 1.5*ck); camLook = V(px*0.25, camLift + 0.5, pz + 5.5);   // 런·계단
camPos = V(0, 4.2, -4.4); camLook = V(0, 0.2, 3.4);                                                          // 로비
camera.position.lerp(camPos, mode==='lobby' ? 1 : Math.min(1, dt*10));
if (shakeT > 0){ shakeT -= dt; camera.position.x += rnd(-1,1)*shakeA; camera.position.y += rnd(-1,1)*shakeA; if (shakeT <= 0) shakeA = 0; }
camera.lookAt(camLook);
```

- `C` = 계단 오르기 중(`CN`, mode `'cannon'`). 이때 플레이어 위치: `sp = clamp(C.pos, 0, C.k − 0.001)`, `pz = C.z0 + sp·0.72`, `py = (floor(sp)+1)·0.42 + sin(frac(sp)·π)·0.12`, `sp < 1`이면 `py = min(py, sp·0.42·1.2)` (L2758).
- `WY` = 현재 지면 높이(계단을 오를 때마다 증가, L937). `dt` = 실시간 dt(상한 0.05, 히트스톱 미적용, §2.8).
- 흔들림은 lerp **뒤에** 위치에 직접 더한다. 다음 프레임 lerp 시작점이 흔들린 위치라 진폭이 조금 남는다. 주시점은 흔들지 않으므로 화면이 살짝 회전도 한다. 정본 방식 그대로 재현한다(D-43).

### 2.2.2 `320_camera` 표 (정본 값, [프로토])

| id | key | anchor | posXMul | posY | posZ | lookXMul | lookY | lookZ | posLerp | snap | liftLerp | blendLerp | fovV | near | far |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 320001001 | run | Player | 0.25 | 13 | −9 | 0.25 | 0.5 | 5.5 | 10 | 0 | 6 | 2 | 52 | 0.1 | 400 |
| 320001002 | climb | Player | 0.25 | 15 | −10.5 | 0.25 | 0.5 | 5.5 | 10 | 0 | 12 | 3 | 52 | 0.1 | 400 |
| 320001003 | lobby | World | 0 | 4.2 | −4.4 | 0 | 0.2 | 3.4 | 0 | 1 | 0 | 0 | 52 | 0.1 | 400 |

열 의미: `anchor=Player`면 위치 = `(px·posXMul, camLift + posY, pz + posZ)`, 주시점 = `(px·lookXMul, camLift + lookY, pz + lookZ)`. `World`면 그대로 월드 좌표. `posLerp` = 위치 보간 계수(`min(1, dt·posLerp)`), `snap=1`이면 즉시. `liftLerp` = 그 모드일 때 camLift 계수. `blendLerp` = 그 모드로 **들어갈 때** ck 계수(run 행 2 = 계단에서 나올 때, climb 행 3 = 들어갈 때). `fovV` = 9:16 기준 세로 FOV(§2.7).

`CameraRig.LateUpdate` 순서(실시간 dt):
1. 모드 판정: 로비 / 런 / 계단(`CN` 있음).
2. `camLift`, `ck` 갱신(위 식, 계수는 표).
3. 목표 위치·주시점 = `lerp(run 행, climb 행, ck)` 결과(위 식의 `13 + 2ck`, `−9 − 1.5ck`와 같다). 로비면 lobby 행.
4. 위치 보간 → 흔들림 가산(§2.2.4) → `transform.LookAt(look, Vector3.up)`.
5. 모든 빌보드 회전 동기화와 `DepthSorter` 실행(§2.3)은 이 뒤.

**로비 → 런 전환.** 로비에서는 화면을 아지트(§2.9)가 그리지만 `GameCamera`는 로비 자세 `(0,4.2,−4.4)→(0,0.2,3.4)`에 계속 둔다. 런 시작 첫 프레임부터 `dt·10` 보간으로 런 자세로 올라간다(약 0.3초에 95%). 이 「낮은 뒤 → 높은 위」 스윕이 정본 감각이므로 로비에서 카메라를 런 자세로 미리 옮기지 않는다.

### 2.3.2 Unity 구현: `DepthSorter`

카메라 거리 기반 기본 투명 정렬(`TransparencySortMode.Perspective`)은 카메라 위치까지의 거리라 정본(전방 깊이)과 다르다. 편향·탐침 높이(+0.8, +0.7)도 넣을 수 없다. 그래서 **정렬 순서를 스크립트가 직접 매긴다.**

- 각 월드 그림 단위(오브젝트·소품·고양이·글자판·이펙트 1회분)의 루트에 `SortingGroup`(레이어 `World`)을 단다. 루트는 `IDepthSortable`을 등록한다: 탐침 월드 위치, 편향, 범주.
- `DepthSorter.LateUpdate`(카메라 갱신 뒤):
  - `d = Vector3.Dot(probe − cam.position, cam.forward)`
  - `d < view.nearCut`이면 루트 숨김.
  - `sortingOrder = −floor((d + bias)·Q)·4 + rank`, `Q = sort.quant`(64), `rank` = 범주 순위.
  - `rank`: 소품·빨랫줄 0, 오브젝트·글자판 1, 고양이·장난감·투사체 2, 이펙트 3. 같은 깊이 칸이면 정본처럼 **먼저 넣은 범주가 뒤(먼저 그림)**.
  - 범위: d ≤ 127 m에서 −32 512 이상(`sortingOrder`는 int16). 안개 끝 84 m·컬링 90 m 안이라 충분하다.
- 글자판은 오브젝트와 따로 루트를 두고 탐침 = 글자판 위치, 편향 −0.05, rank 1.
- 우물 벽돌처럼 **그룹 안에서도 깊이 순**인 것은 그 그룹 안 자식 `sortingOrder`를 같은 식(정수 범위 0~999로 정규화)으로 매 프레임 다시 매긴다(L3644~3650 「먼 것부터」).
- 이펙트는 [06](06_Effects.md)의 `EffectManager` 핸들 루트를 `DepthSorter`에 등록해 매 프레임 갱신한다. 생성 때 한 번 정한 값을 고정하면 카메라가 앞으로 가며 월드 쪽 순서만 바뀌어 어긋난다.

### 2.4.3 지면 `GroundStripMesh`

정본과 같은 띠를 CPU에서 만든다(쿼드 약 46띠 × 12개 ≈ 550개, 매 프레임 정점색 갱신).

- 띠: `z`를 `floor(zF/2)·2`부터 `floor(zN/2)·2`까지 2씩 내림(먼 띠부터). 구간 `[max(z, zN), z+2]`. 절벽 z가 띠 안이면 두 조각.

- 띠 안 사각형(모두 y 고정, x 범위, 색은 `mixC(…, th.fog, fk)`):

### 2.5.2 테마 소품 배치 `PropStreamer` (`buildEnv` L1274~1284)

- z = `floor((from − 30)/3.2)·3.2`(계단 뒤 새 지형이면 `from + 1.6`)부터 `from + len + 140` 미만, 3.2 m 간격. 양쪽 `sd = ±1`.
- `r1 = hash(z·1.31 + sd·7.7)`, `r2 = hash(z·2.17 + sd·3.1)`, `r3 = hash(z·0.73 + sd·9.9)`, `r4 = hash(z·3.7 + sd·1.3)`.

- 달동네 분기는 소품 그룹 스케일(0.8 + r·0.6)을 **쓰지 않는다**(L3570, L3592의 s는 스케일 없는 `pj` 값).

## 2.6 외곽선·명암 도우미

### 2.6.1 색 상수와 함수

| 이름 | 정본 | Unity |
|---|---|---|
| OLC | `#4a3446` 모든 외곽선 공통(L2804) | `view.outlineColor` |
| shadeC(c, k) | `k > 0`: 흰색 쪽 `lerp(k)`, `k ≤ 0`: `×(1+k)`. 결과 `#rrggbb`(L2801) | `MvColor.Shade(c, k)` |
| mixC(a, b, k) | `a→b` 선형, **k를 1/20 단위 내림**(`(k·20|0)/20`)(L2802) | `MvColor.Mix(a, b, k)`(양자화 `view.mixQuant`) |
| ha(c, a) | 알파 2자리 붙임, `round(a·255)` | `MvColor.WithAlpha` |

- 계산은 sRGB 0~1 값에서 그대로 한다(선형 변환 없음). 정본 three r128의 `getHexString`은 `×255` 후 비트 연산으로 **내림**한다 [추정: r128 `Color.getHex` 구현]. 결과 채널 ±1 차이는 허용 오차.
- 테마색에서 파생되는 색(줄눈·그늘·윗면)은 테마 로드 때 한 번 계산해 캐시한다.

### 2.6.2 외곽선 굵기

정본 외곽선은 대부분 `max(1, s·k)` px(k = 0.035~0.06). 스프라이트는 기준 크기에서 굽는다(§2.1.3 규칙 5). 절차 메쉬(`BoxBillboard`, 담장, 지면 옹벽 윗선)는 **변마다 굵기 lw 띠 쿼드**를 채움 위에 그린다(캔버스 stroke는 변 중심선 기준이라 안팎 반씩).

### 2.6.3 그라데이션·하이라이트

캔버스 선형 그라데이션은 정점색 보간으로 같다(사각형 위·아래 정점에 두 색). 예: `drawBox` 정면 위 `shadeC(col, 0.04)` → 아래 `shadeC(col, −0.14)`.

### 2.6.4 `BoxBillboard` (`drawBox` L2809~2820)

정본은 진짜 상자가 아니라 「정면 + 오른쪽으로 기운 윗면」 그림 한 장이다. 앵커 = **앞면(카메라 쪽) 아래 가운데** `(x, y, z − d/2)`.

빌보드 로컬 좌표(m, y 위가 +)로 옮긴 모양:

| 부품 | 정점(로컬 m) | 색 |
|---|---|---|
| 오른쪽 그늘 띠 | x `w/2 ~ w/2 + 0.04w`, y `0 ~ h + T/2` | `shadeC(col, −0.28)` |
| 윗면(평행사변형) | `(−w/2, h) → (−w/2 + 0.06w, h+T) → (w/2 + 0.04w, h+T) → (w/2, h)` | `topCol` 또는 `shadeC(col, 0.18)`, 외곽선 OLC |
| 정면 | `(−w/2, 0) ~ (w/2, h)` | 세로 그라데이션 위 `shadeC(col, 0.04)`, 아래 `shadeC(col, −0.14)` |
| 위 하이라이트 | 정면 위쪽 높이 `clamp(0.06h, 1/s, 3/s)` | `rgba(255,255,255,.18)` |
| 외곽선 | 정면 사각형 + 윗면 | OLC, 굵기 `clamp(0.035, 1/s, 3/s)` m |

- 윗면 두께 `T = max(2, min(d·s·0.32, H2·0.6 + 6))` px → 로컬 m로 `T = max(2/s, min(0.32·d, 0.6h + 6/s))`. 집(d 3.6, h ≥ 2.2)은 항상 **1.152 m 고정**, 우다다 입구 계단(d 0.8)은 0.256 m. 매 프레임 s로 다시 계산해도 되지만 집·계단은 상수로 충분하다.
- 그리는 순서: 그늘 띠 → 윗면 → 정면 → 하이라이트 → 정면 외곽선(L2812~2818).
- 카메라 x가 바뀌어도 윗면 기울기는 고정이다. 이것이 정본 모양이다(D-44).
- 반환값(`x0, y0, w, h, cx, T`)은 문·창 배치에 쓴다: 문 x = `cx + (hh−0.5)·w·0.4`, 창 y = `y0 + h·0.25` 등(E 노트 §4.7).

### 2.6.5 담장 `fence`

월드 메쉬(YZ 평면, x = `sd·4.78`). 안쪽 면 x = `x − sd·0.2`, z `wp.z ± 1.58`, 높이 1.25, 색 `walls[floor(hh·len)]`. 아래 그늘 띠 0.22 `shadeC(col, −0.12)`. 윗면 두께 0.4(x `xi ~ x + sd·0.2`) `wallTop`. 장식(차양 6칸·대문·꽃·눈 캡)은 같은 평면 위 쿼드. 수치는 E 노트 §4.7(a).

### 2.7.3 확장에 따라 바뀌는 값

- **지면 끝**: 9:21에서는 화면 맨 위 광선이 지면과 플레이어 앞 약 82 m에서 만난다. 정본 지면 끝(`PZ+92` = 플레이어 +83)에 걸리므로 Unity는 `view.groundFar`를 **120**으로 늘린다. 안개(플레이어 +90.7에서 완전)가 덮어 정본 화면과 차이 없다.
- **드래그 감도**: 정본 `drag.px + dx/(W/7.2)`(L3844) → 화면 폭 전체 드래그 = 7.2 m. Unity는 W 대신 **기준 프레임 폭**(가로 확장 시 `H·9/16`, 세로 확장 시 화면 폭)을 쓴다. 입력 담당([04](04_GameRules.md))에 기대하는 가정.
- **화면 공간 그림**(우다다·눈·비네트·집중선): 정본 식의 W·H는 실제 월드 뷰포트 크기를 그대로 쓴다(비례식이라 늘어난 화면을 채운다).

### 2.7.4 기준 px

정본의 고정 px 상수(눈 반지름 1~3.2, 별 2 px, 선 굵기, 우다다 글자 테두리 등)는 폰 스테이지 폭(약 358~360 CSS px)에서의 값이다. Unity 변환: `1 기준 px = 화면 폭(기준 프레임 폭) / view.refWidthPx(360)`. `ScreenRig`의 로컬 단위도 이 기준 px다.

### 2.8.2 Unity 규칙: `MvTime`

`Time.timeScale`은 쓰지 않고(항상 1) 게임이 시간을 직접 나눈다. `Time.maximumDeltaTime`은 배속과 충돌하므로 상한으로 쓰지 않는다.

| 시간 | 식 | 쓰는 곳 |
|---|---|---|
| realDt | `min(time.dtCap, Time.unscaledDeltaTime)` | 카메라·흔들림·팝업·빌보드 애니(고양이 위상 제외)·토스트 타이머·히트스톱 감소·손패 머지 |
| gameDt | `realDt · (히트스톱 중 && 모드 run ? time.hitStopScale : 1)` | `MV.Run.Step` (배속 ts회 반복) |
| simDt | `gameDt · ts` | 계단 오르기, 룰렛, 이펙트([06](06_Effects.md)) |
| 실시간 ms | `Time.unscaledTimeAsDouble` | 정본의 `performance.now()` 사용처: 장난감 회전, 츄르 출렁, 전구 깜빡임, 눈, 빨래 흔들림, 우다다 별·단계 이름·집중선·종료 섬광 |
| 실시간 타이머 | 위 ms 기준 | 정본 `setTimeout`·CSS 전환: flyTo 560 ms, 배너 1.5 s, 플래시, 카드 비행 620 ms([06](06_Effects.md)) |

| id | key | value | unit | 근거 |
|---|---|---|---|---|
| 300001001 | time.dtCap | 0.05 | s | L3825 |
| 300001002 | time.hitStopScale | 0.12 | 배 | L3827 |
| 300001003 | time.targetFps | 60 | fps | [창작] D-43 |

- 히트스톱은 **런 모드에서만** 느리게 한다. 계단·결과 중에 요청이 와도 `hitStop`은 줄기만 한다(L3826).
- 배속 ts(테스트 패널 ×1/×2/×3)는 개발 빌드만.
- 프레임 수 의존 값: 로비 `AZ.emote += 1/60`(L3533), `AZ.bump −0.03`/프레임(L3515), 흔들림 난수(프레임마다 새 값). 60 fps 고정(D-43)이면 프레임 단위 그대로, 아니면 `·realDt·60`으로 환산한다.

## 2.9 로비 장면(아지트)

정본은 로비에서 `drawAzit()`만 그리고 끝낸다(L3780). 카메라·안개·틴트·가산광·이펙트·정렬 목록 모두 쓰지 않는다. `#vig` 비네트는 여전히 위에 있다.

| 항목 | 런 | 로비 |
|---|---|---|
| 투영 | 원근(`pj`) | **아이소메트릭 화면 비례식** `iso(u, v) = (cx + (u − v)·A, cy + (u + v)·B)`, `cx = W/2`, `cy = H·0.548`, `A = W·0.4`, `B = A·0.52`, u, v ∈ [−1, 1] (L3475~3477) |
| 정렬 | 깊이 내림차순 | 시설·고양이를 **화면 y 오름차순**(위 = 뒤 먼저) |
| 크기 단위 | s px/m | `s = W·0.115`(시설·고양이 1 단위) |
| 안개·틴트·가산광 | 있음 | 없음(난로 불빛·전구 광륜은 아지트 자체 그림) |
| 시간 | 게임·실시간 | `t = lobbyT`(실시간 누적), `AZ.emote`·`AZ.bump`는 프레임 단위 |

Unity 권장: `LobbyStage` = 별도 직교 카메라 `LobbyCamera`(URP Base, 로비일 때만 켬, `GameCamera`는 끔). 직교 크기 = 8, 기준 프레임 9×16 단위(1 단위 = W/9). 아지트 그림은 이 단위로 `iso()` 식에 따라 배치한 스프라이트, `sortingOrder`는 화면 y로 매 프레임 계산. 세로로 긴 화면은 기준 프레임을 세로 가운데에 두고 위(벽 색 `#7a5462`/`#8a646c` 연장)·아래(바닥 바깥 `#2e2230`)를 채운다. 그리는 순서·수치는 E 노트 §6.14, 그림은 [03](03_ResourcePipeline.md), 위 UI는 [05](05_Screens.md).

런 시작: `LobbyCamera` 끔 → `GameCamera` 켬(자세는 로비 자세에서 보간 시작, §2.2.2). 정본도 전환 프레임에 바로 골목을 그린다(페이드 없음).
