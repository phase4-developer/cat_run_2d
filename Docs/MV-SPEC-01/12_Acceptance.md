# 12. 인수 기준 — 「똑같다」 판정과 표 확장 시험

[입구](README.md) · 앞: [11 작업 계약](11_WorkContracts.md) · 다음: [13 결정](13_Decisions.md)

완성품 조건 두 가지([01 §1.1](01_Scope.md))를 숫자로 판정한다. 겉은 **같은 상태에서 찍은 캡처 대조**와 **로직 덤프 대조**로, 속은 **코드 수정 없이 행만 추가하는 시험**으로 본다.

## 12.1 원칙

1. **같은 상태로 만든 뒤 비교한다.** 눈으로 비슷한지 보지 않는다. 프로토와 Unity에 같은 저장 상태, 같은 난수, 같은 시간, 같은 입력을 넣고 같은 해상도로 찍는다(도구는 MV-QA-HARNESS, [11](11_WorkContracts.md)).
2. **정본은 고치지 않는다.** 프로토 쪽 조작은 Playwright가 페이지에 주입하는 스크립트로만 한다. 정본 SHA256이 [01 §1.2](01_Scope.md)와 같은지 매번 먼저 확인한다.
3. **로직과 그림을 나눠 본다.** 로직(생성·시뮬·정산)은 숫자 덤프로 정확히 맞추고, 그림은 허용 오차로 본다. 로직이 맞지 않으면 그림 대조를 하지 않는다.
4. **사람 확인은 따로 적는다.** 손맛·청취·신규 화면(컨텐츠 메뉴) 디자인처럼 자동 판정이 안 되는 것은 사람 확인 항목으로 두고, 확인 전에는 NOT_RUN이다.

### 12.1.1 프로토 쪽 고정 방법 (주입 스크립트)

| 대상 | 방법 |
|---|---|
| 화면 크기 | 뷰포트 1080×1920, `deviceScaleFactor` 1 → `PR2 = min(2, 1) = 1`, 스테이지 1080×1920(9:16, L943~948) |
| 난수 | `Math.random`을 감싼다. 기본은 시드 PRNG(mulberry32, 시드는 장면 정의). 호출마다 `(값, 호출 함수 이름)`을 기록한다(`new Error().stack` 첫 게임 함수). 로직 대조용 덤프에는 **로직 함수에서 나온 값만** 순서대로 남긴다(12.3.2) |
| 시간 | `performance.now`·`Date.now`를 가짜 시계로 바꾸고 `requestAnimationFrame`을 끊은 뒤 하네스가 `frame()`을 직접 호출한다. 프레임 dt는 1/60초 고정 |

| 대상 | 방법 |

## 12.3 로직 대조 (MV-RUN, MV-META)

### 12.3.1 덤프 종류

| 덤프 | 내용 | 범위 |
|---|---|---|
| GEN | `buildLevel` 결과 오브젝트 목록(종류·x·z·hp·hw·hd·보상·게이트 값) | Level 1~20 × Area 1~15 × Floor 1~3, 프리셋 3종 |
| SIM | 프레임별 플레이어 x·z, 오브젝트 hp·상태, 투사체 수, 재화, 게이지, RunEvent 목록 | 장면 정의 W-02~W-10의 입력 기록 + 런 전체 3판(입력 기록) |
| META | 강화 비용·효과, 정산 결과(gold·dia·souls·tok), Area 개방, 부활 특전 | P=0~MAX 전부, 정산 시나리오 20개 |

### 12.3.2 난수 기록 재생

프로토는 그림 효과(FX·흔들림)와 로직이 같은 `Math.random`을 나눠 쓴다. Unity는 로직 난수(`RunRng`)와 표시 난수를 나눈다([04](04_GameRules.md) 난수 절). 그래서 로직 대조는 시드 공유가 아니라 **기록 재생**으로 한다.

1. 프로토 하네스가 모든 `Math.random` 호출을 `(순번, 값, 호출 함수)`로 기록한다.
2. 호출 함수가 로직 목록(04 난수 절의 「로직」 표)에 있는 값만 골라 순서대로 덤프한다.
3. Unity 시험은 그 값을 순서대로 돌려주는 `ReplayRng`를 `MV.Run`에 넣고 같은 입력을 재생한다.
4. Unity 쪽 로직이 덤프보다 난수를 더 쓰거나 덜 쓰면 그 자리에서 실패로 본다(호출 순서 불일치).

### 12.3.3 허용 오차

| 값 | 기준 |
|---|---|
| 정수(hp 반올림 값, 재화, 칸 수, 카드 수, 레벨) | 완전 일치 |
| 좌표·속도·게이지(float) | 절대 오차 1e-4 이하. `MV.Run`은 JS와 같은 **double** 연산을 권장한다(오차 누적 방지) |
| 이벤트 | 프레임 번호·종류·대상 완전 일치 |
| `hash`(sin 기반) 결과 | 생성 덤프의 결과 표로 고정해 완전 일치([07](07_Tables.md) `313_fieldGen` 고정 방법) |

## 12.4 그림 대조 (캡처)

### 12.4.1 지표

| 지표 | 계산 | 월드 장면 | UI 장면 | 이펙트 장면 |
|---|---|---|---|---|
| SSIM(휘도, 창 11px) | 전체 화면, 마스크 제외 | ≥ 0.93 | ≥ 0.95 | ≥ 0.85(연속 3프레임 평균) |
| 색 차 | 같은 화소 ΔE2000 평균 | ≤ 3.0 | ≤ 2.0 | ≤ 5.0 |
| 색 차 상위 | ΔE2000 99백분위 | ≤ 15 | ≤ 12 | — |
| 위치 | 기준점(오브젝트 앵커, UI 요소 모서리)의 화면 좌표 차 | ≤ 4px | ≤ 3px | ≤ 6px |
| 크기 | 기준 요소 경계 상자 너비·높이 비 | ±3% | ±2% | ±5% |
| 개수 | 보이는 오브젝트·파티클·팝업 개수 | 완전 일치 | 완전 일치 | ±10% |

- 글자 영역은 래스터라이저 차이(브라우저 vs TMP SDF)가 있어 SSIM 계산에서 **마스크**하고, 대신 글자 경계 상자의 위치·크기·색만 본다. 마스크는 장면 정의 `mask[]`에 사각형으로 적는다.
- 안티앨리어싱 차이를 줄이려고 양쪽 캡처를 2×2 평균으로 줄인 540×960에서도 SSIM을 한 번 더 계산하고, 둘 중 큰 값을 쓴다.
- 기준값은 첫 통합 지점에서 실측해 조정할 수 있다. 조정하려면 장면 3개 이상의 실측표와 이유를 원장에 남기고 총괄이 승인한다(완화만이 아니라 강화도 같은 절차).

### 12.4.2 실패 처리

- 하나라도 기준 밖이면 그 장면은 FAIL이다. 차이 히트맵(ΔE 색칠)과 두 캡처를 보고서에 붙인다.
- 원인을 「로직」(12.3 먼저 확인), 「투영·카메라」(02), 「그림 추출」(03), 「셰이더·테마」(02), 「UI 배치」(05)로 분류해 해당 계약에 되돌린다.

### 12.4.3 리소스 단위 대조 (MV-TOOL-ART)

추출 PNG 하나하나를 정본에서 같은 함수·인자로 그린 캔버스와 비교한다(같은 도구 안). 기준: 화소 완전 일치(같은 브라우저가 같은 코드로 그리므로). 아틀라스 압축 뒤에는 ΔE2000 평균 ≤ 2.0, 99백분위 ≤ 10.
